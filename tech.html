21. Gameplay Ability System (GAS)

Каждое действие персонажа — спринт, ADS, перезарядка, ближний бой, взлом — реализовано как отдельный UGameplayAbility-подкласс. GAS обеспечивает сетевое предсказание, тег-based блокировку несовместимых состояний и легко расширяемую систему эффектов без ручного менеджмента состояний.

Почему GAS, а не ручные state machines?
GAS даёт сетевое предсказание из коробки: клиент активирует способность локально, сервер валидирует. Тег-based блокировка исключает эксплойт-комбо (например, стрелять во время перезарядки) без написания спагетти-условий в Character.cpp. Расширение новой способностью — отдельный класс, без правки существующего кода.

22. Архитектура Animation Blueprint

Анимационная система построена на трёх независимых слоях, которые комбинируются в финальную позу. Такой подход позволяет независимо менять локомоцию, верхний ADS-оверрайд и процедурные эффекты без конфликтов между аниматорами и программистами.

23. Enhanced Input System

Вся логика ввода построена на Enhanced Input (UE5). Это отделяет «физическую клавишу» от «игрового действия», позволяя менять раскладку без изменения кода, поддерживать геймпады/KB&M одновременно и обрабатывать сложные паттерны (hold, double-tap, combo).

Клиентское предсказание и Lag Compensation

Двусторонняя система: клиент предсказывает движение локально (нет задержки управления), сервер авторитарно валидирует и при расхождении отправляет коррекцию. Для регистрации выстрелов сервер «откатывает» позиции игроков на момент клиентского выстрела.

4-шаговый цикл предсказания

Client-Side Prediction Flow
① PREDICT — клиент применяет ввод локально Input{W, sprint, aimDir} → клиент двигает персонажа немедленно Сохраняет FSavedMove_NF в кольцевой буфер (64 входа) ② SEND — клиент отправляет пакет серверу {InputFlags, Timestamp, StartLocation, StartVelocity} ③ VALIDATE — сервер симулирует тот же ввод Если |ServerPos - ClientPos| < Threshold → OK, подтверждение Если расхождение → отправить коррекцию клиенту ④ CORRECT — клиент получает коррекцию Принять серверную позицию Переиграть все неподтверждённые ходы из буфера Визуально: плавная интерполяция (не телепорт) Используется в: CS2, CoD, Overwatch, Valorant, UE5 В UE5: CharacterMovementComponent имеет это из коробки

Система респауна

Spawn Algorithm
Для каждой точки рассчитывается Score: Score = W_safety * SafetyScore + W_team * TeamProximityScore + W_enemy * EnemyDistanceScore + W_obj * ObjectiveScore + W_recent * RecentDeathPenalty SafetyScore: нет прямой видимости врагов (raycast) TeamProximity: рядом с союзниками (но не слишком) EnemyDistance: далеко от врагов ObjectiveScore: рядом с активными целями RecentDeath: не спаунить где только что убили Точка с максимальным Score выбирается.

SBMM — Матчмейкинг на основе навыков

Скрытый рейтинг (MMR) рассчитывается отдельно для каждого режима. Ранговый режим использует строгий SBMM, казуальный — мягкий диапазон с приоритетом качества соединения.

Модель рейтинга и анти-буст

MMR Model
РЕЙТИНГОВАЯ МОДЕЛЬ: ├── Основа: Elo-производная, отдельно для каждого режима ├── K-фактор: 32 (новые аккаунты, первые 50 матчей) │ 16 (после 50 матчей) ├── Размещение: первые 10 матчей — широкое окно ±300, │ результат ×2 для delta MMR └── Группы: MMR лобби = среднее группы ± 20 за каждого ЗАЩИТА ОТ БУСТА И СМУФИНГА: ├── Резкое падение MMR > 200 за 5 матчей → флаг ручной проверки ├── Smurf detection: возраст аккаунта × аномалия win-rate ├── Killcam и replay хранятся 30 дней для расследований └── Ban wave: банятся аккаунты, а не hardware ID (обход через новый акк)
SBMM vs CBMM (connection-based): чистый SBMM убивает казуальные лобби для высокорейтинговых игроков — они всегда в «работе». Гибридный подход: Ранговый — строгий SBMM, Казуальный — сначала качество соединения (ping < 80ms), затем мягкий диапазон MMR. Это снижает нагрузку на высокорейтинговых игроков и увеличивает retention.

Тик-рейт сервера и ощущение сетевого кода

Тик-рейт — это частота, с которой сервер обрабатывает игровое состояние и рассылает обновления клиентам. Это один из самых недооценённых параметров, напрямую влияющий на воспринимаемую честность игры.

Tick Rate — The Math
БАЗОВЫЕ ЦИФРЫ: Tick rate = 64 Hz → обновление каждые 15.6ms Tick rate = 128 Hz → обновление каждые 7.8ms ПРИМЕР: Игрок А стреляет в Игрока Б При 64 Hz: Игрок А нажимает огонь → сервер получает через 0–15.6ms Максимальная задержка регистрации выстрела: RTT/2 + 15.6ms При RTT=50ms: 25ms + 15.6ms = 40.6ms окно При 128 Hz: Максимальная задержка: RTT/2 + 7.8ms При RTT=50ms: 25ms + 7.8ms = 32.8ms окно РАЗНИЦА: ~7-8ms — незначительна для глаза (порог ~50ms) НО: уменьшает ВАРИАТИВНОСТЬ позиции игроков в lag compensation → меньше случаев «я попал но промазал» СТОИМОСТЬ: 128 Hz = ×2 CPU нагрузка на сервер 64 Hz: ~30–50 игроков/ядро 128 Hz: ~15–25 игроков/ядро
Параметр64 Hz128 HzНаш выбор
Окно обновления15.6ms7.8ms64 Hz казуальный / 128 Hz ранговый
CPU/серверНизкий×2—
Bandwidth (сервер→клиент)~40 KB/s/игрок~80 KB/s/игрок—
Воспринимаемая честностьХорошаяОтличнаяРанговый заслуживает
ПримерыCoD, BattlefieldCS2, Valorant (ранговый)—
Почему не всегда 128 Hz? CS2 использует 128 Hz тик только в матчмейкинге уровня Premier/Faceit — казуальные сервера работают на 64 Hz. Это прагматичное решение: разница в геймплее ощущается только на уровне 2000+ ELO. Для большинства игроков пинг и стабильность соединения важнее тик-рейта.

28. World Partition и бюджет памяти

Все мультиплеерные карты используют World Partition — автоматическую систему стриминга уровня UE5. Контент делится на ячейки, которые подгружаются и выгружаются по мере движения игрока.

World Partition Config
Размер ячейки: 64m × 64m Расстояние загрузки: 2 ячейки вперёд по направлению движения Расстояние выгрузки: 4 ячейки от игрока (гистерезис) Level Instances для разрушаемых объектов: ├── Chaos-кластеры предфрактурированы offline ├── Стримятся как отдельные Level Instance per zone ├── При разрушении: замена на динамический Chaos actor └── Limit: 8 активных Chaos объектов одновременно HLOD (Hierarchical LOD): ├── Автоматически генерируются для каждой ячейки ├── Показываются при >200m от игрока └── Nanite mesh + слияние материалов

31. Соревновательный / Ранговый режим

Ранговый режим — это отдельная экосистема. Те же механики, но другой социальный контракт: каждое действие имеет ставку, результат публичен, прогресс сохраняется через сезоны. Дизайн должен поощрять командную игру и честную конкуренцию.

Ранговая структура

Механика ранговых очков (RP)

Rank Points System

Сезонная система

Season Design
СЕЗОН = 90 дней: ├── Начало: все игроки проходят 5 placement матчей │ (ранг с прошлого сезона: мягкий откат на 1 тир) ├── Финальные 2 недели: «Конец сезона» — RP множитель ×1.5 ├── Конец: «Снимок» финального ранга → ранговые награды └── Сброс: все игроки начинают с нуля (Бронза+) СЕЗОННЫЕ НАГРАДЫ (привязаны к финальному рангу): ├── Бронза: Calling Card «Сезон N» ├── Серебро: Эмблема + Calling Card ├── Золото: Баннер игрока + звук победы ├── Платина: Уникальный скин оружия (нельзя купить) ├── Элита: Анимированный значок + скин оружия └── Мастер+: Персональный флаг + инвайт на турнир
Почему killstreak ограничен до 5K в ранговом? 7K+ killstreak (вертолёт, дрон) создают ситуации, когда навык управления killstreak'ом важнее навыка стрельбы. В казуальном это нормально — это веселье. В ранговом это искажает измерение навыка. CS2 и Valorant вообще без killstreak — мы идём на компромисс, оставляя информационные (3K UAV) и зональные (5K арт) как инструменты командной игры.
